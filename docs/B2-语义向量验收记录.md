# B2 · 真实语义向量 —— 验收记录

> 对应《优化落地与工业化升级方案 v2.2》第 5 章。记录日期 2026-09-05。
> 环境:Node v26.3.0,Windows 10 x64,纯 CPU。

## 0. 一句话结论

`bge-small-zh-v1.5`(ONNX int8,512 维)已在**纯 WASM、零原生二进制、可断网**的前提下接入检索链路。
与 SOP 原文几乎没有字面重叠的语义化查询,Top1 命中从 **6/10 提到 8/10** —— 这正是方案 5.4 指定的核心演示点。
模型缺失时整链路降级到确定性哈希向量,**检索不中断**,由 21 条单测钉住。

## 1. 选型偏离:没有用 transformers.js(方案 5.1)

方案 5.1 写的是 `npm install @huggingface/transformers`,5.2 的评审补强又要求
「强制 WASM 后端、不引入原生二进制」。**这两条在 transformers.js v4 下无法同时满足**,
三条独立证据(均在本机实测):

| # | 现象 | 证据 |
|---|---|---|
| 1 | `onnxruntime-node`(211 MB,含 `.node` 原生二进制)是它的**非 optional** 依赖 | `deps` 里就有,`optionalDependencies` 为 undefined;装完必然进依赖树 |
| 2 | 本机加载该原生绑定直接失败,且发生在 **import 阶段** | `require("onnxruntime-node")` → `A dynamic link library (DLL) initialization routine failed.`;`import dist/transformers.node.mjs` 同错 |
| 3 | 换 web 入口能绕开原生绑定,但**读不了本地模型** | `dist/transformers.web.js` 把 `node:fs` stub 成空对象(`IS_FS_AVAILABLE=false`),而 `loadResourceFile` 在 `IS_NODE_ENV` 下需要 `FileResponse.filePath` → `Unable to get model file path or buffer.` |

第 3 条直接否掉方案 5.2 的「模型预置到打包目录 + `env.allowRemoteModels=false`」——
那条路在 Node 下只能联网拉 HuggingFace,与「断网可跑」冲突。
附带成本:它还拖进 `sharp`,`npm audit` 从 9 条涨到 12 条。

**替代实现**:`onnxruntime-web` 的 `/wasm` 子入口(纯 JS + `.wasm`)+ 自研 WordPiece 分词。
BERT 分词是完全确定性的规则算法、没有任何权重,照搬 HF `BertTokenizer` 的四步即可
(见 `src/server/rag/wordpiece.ts`,22 条单测覆盖)。

依赖树增量:

```
onnxruntime-web@1.26.0-dev
├── onnxruntime-common@1.24.0-dev
└── protobufjs@7.6.6
```

三个包**全部纯 JS**。改造后 `npm audit` = **9 条,与改造前逐条相同**
(`sharp` 属于 `next`;`protobufjs` 属于 `onnxruntime-web`,无新增告警)。
「零原生依赖」这条项目根属性保持不变。

## 3. 两处与方案示例代码相反的实测结论

方案的示例片段是从通用 sentence-transformers 抄来的,两处口径与 bge 作者的实际约定不符。
都用同一组 10 条查询实测后按**模型自带口径**定案:

| 参数 | 方案示例 | 实测 Top1 | 采用 | 理由 |
|---|---|---|---|---|
| pooling | `mean` | cls **8/10** vs mean 7/10 | **`cls`** | FlagEmbedding 对 bge 系的默认就是 CLS |
| `do_lower_case` | (未提) | false **8/10** vs true 7/10 | **`false`** | 模型 `tokenizer_config.json` 自带值 |

`do_lower_case` 这条值得单独说明:词表 21128 个 token 里**没有任何大写 token**,
所以 `DV200` / `FFPE` / `RNA` 会落到 `[UNK]` 或子词 —— 强制小写看起来是明显的修复。
实测反而更差。原因是这类精确缩写本来由 **BM25 字面通道**负责,语义通道不需要认识它们;
强制小写只是把中文语义表示也一起扰动了。两条结论都固化成了单测断言,防止后人「顺手优化」。

## 5. 双向量空间的裁决(实现要点)

语义向量 512 维、哈希向量 256 维,**量纲与维度都不可比**。而 `cosine()` 用的是
`Math.min(a.length, b.length)`,混算不会报错,只会静默产出无意义的相似度。

因此 `chunks` 表两列并存(`embedding` NOT NULL / `embedding_semantic` 可为 NULL),
每次检索做一次**全有或全无**的空间裁决:

| 条件 | `vectorSpace` | `vectorSpaceReason` |
|---|---|---|
| 没传查询侧语义向量(模型不可用) | `hash` | `no-query-vector` |
| 传了,但**任一**候选未回填 | `hash` | `candidates-not-backfilled` |
| 传了,且候选全部已回填 | `semantic` | `null` |

被否掉的两个方案及理由:

- **给缺失候选补 0** —— 凭空压低它们的分,等于静默降权,排序污染不可解释;
- **两个空间分别归一化后合并** —— 把两个不可通约的量纲混进同一个排序。

宁可整体降级:行为可解释、可回滚,而且 `vectorSpaceReason` 直接落进 checkpoint 可离线统计。

## 6. 降级契约(方案 5.4 硬验收项)

| 失败点 | `semanticUnavailableReason()` | 行为 |
|---|---|---|
| `NP_DISABLE_SEMANTIC=1` | `disabled` | 不加载模型 |
| 模型目录缺失/文件不齐 | `model-missing:<dir>` | 不加载模型 |
| WASM/会话创建失败 | `load-failed:<msg>` | 记一次日志后短路,不重试 |
| 推理抛错 | `inference-failed:<msg>` | 同上 |

四种情况一律返回 `null`,**绝不**在 `embedSemantic()` 内部偷换成哈希向量。
空间选择只在 `retrieval.ts` 一处发生。

实测(`src/server/rag/semantic.test.ts`,21 条):

- 模型目录不存在 → `modelPresent()` 为假、`embedSemantic()` 返回 null、检索照常出结果、
  `vectorSpace=hash`、**引用号照常绑定**(降级不能把 citation 弄丢,否则直接触发 NovaGuard);
- 只有 `config.json` 的「半个模型」也判为不可用(比完全没有更危险 —— 会一路走到会话创建才炸);
- 模型缺失时入库仍然成功,语义列留空,哈希列 256 维完好;
- 模型缺失时回填是无害空操作,`written=0` 且不改动任何行;
- `NP_DISABLE_SEMANTIC=1` 逃生开关生效。

## 7. 回填(B2-2)

`backfillSemanticVectors(db)` 按「缺哪条补哪条」(`WHERE embedding_semantic IS NULL`),
不是按「是否刚建库」。这一点是必须的:

> 首页的 `ensureSeeded()` 是**同步**的(React server component 里不适合等 24 MB 模型),
> 它先把库种完,此时 `chunkCount !== 0`;若按「刚建库才补」写,运行时就**永远不会**写语义向量。
> 存量 v2 库升级、以及 B3 的批量入库同理。

- 幂等:第二次跑 `scanned=0`;
- 支持分批(`{ batch: n }`);
- 只补空缺,已有向量不被重算覆盖;
- 模型中途失效即 `break`,不继续白烧 CPU;
- CLI 入口:`npm run model:backfill`。

## 8. 数据库迁移

`SCHEMA_VERSION` 2 → 3。`CREATE TABLE IF NOT EXISTS` 不会给已存在的表补列,
所以新增列走 `ADDITIVE_COLUMNS`(`PRAGMA table_info` 探测 + `ALTER TABLE ADD COLUMN`),
排在 `SCHEMA_SQL` 之后、FTS 回填之前。列可为 NULL 且无默认值,SQLite 下是 O(1) 操作。
存量库直接原地升级,无需重建。

## 12. 口径修正(方案 5.2 要求)

引入真实向量后,「离线确定性」的表述必须收紧:

- 旧:全链路确定性
- **新:检索通道可确定性降级**

量化 ONNX + 单线程 WASM 在同一平台上逐位可复现(已由「同一句话两次编码逐位一致」单测钉住),
但跨平台/跨版本的浮点行为不保证逐位相同。真正**无条件确定性**的是哈希向量通道,
它随时可通过 `NP_DISABLE_SEMANTIC=1` 接管全链路。
