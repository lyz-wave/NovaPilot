# B3 · 知识摄取管线与语料扩充 —— 验收记录

> 对应《优化落地与工业化升级方案 v2.2》第 6 章,以及《量化指标体系 v1.1》第 12 节四处埋点。
> 记录日期 2026-09-06。环境:Node v26.3.0(`node:sqlite` 内置 FTS5),Windows 10 x64,纯 CPU。

## 0. 一句话结论

`data/knowledge/*.md` 现在是**可版本管理的一等知识源**:8 篇新 SOP(32 chunk)经
`npm run kb:ingest` 挂在 NovaBench 金标回归门禁上入库,门禁 `proceed` 才 COMMIT、
`stop` 就整批 ROLLBACK,**门禁没过的知识一个 chunk 都不留**(2 条事务级单测钉住)。
知识库从 7 篇 / 22 chunk 扩到 **15 篇 / 54 chunk**,54/54 全部带 512 维真实语义向量、
54 行 FTS5 影子表同步。同时补齐指标体系第 12 节点出的**四处埋点缺口**,并新增
`latency_samples`(第 10 节要求延迟与防线结构成对看,而系统里原本一个延迟数都没落库)。

## 1. 知识源格式:平铺 frontmatter,不引 YAML

`FrontmatterSchema`(zod,9 个必填字段)刻意只支持 `key: value` 平铺格式:

| 字段 | 约束 | 作用 |
|---|---|---|
| `id` | 非空 | 检索侧文档主键,与种子库同名空间 |
| `source` | `SOP` \| `SCI` | 证据类型,进卡面 |
| `title` / `citation` / `version` / `appliesTo` | 非空 | 引用号反查(埋点 A)所需的可核实字段 |
| `validUntil` | `YYYY-MM-DD` 正则 | 过期证据判定 |
| `lang` | `zh` \| `en` | — |
| `validation` | `verified` \| `conflict` \| `expired` | NovaGuard 的证据有效性输入 |

不引 YAML 依赖是硬约束(项目的零原生依赖 / 最小依赖树属性),而知识库元数据本来
就不需要嵌套结构。`#` 之后**不**当注释处理 —— SOP 标题里可能真有 `#`。

`ParsedDocument extends IndexableDocument`:摄取进来的文档和内置种子库在检索侧
**完全同构,没有「二等证据」**。这不是洁癖 —— 如果外部知识在打分或卡面上有区别,
「入库量」这个激励指标就可以靠灌一堆低权重文档来刷。

## 2. 分块策略与实测块长

目标区间 `CHUNK_MIN=300` / `CHUNK_MAX=500` 字,按**二级标题 + 自然段**递归分块。
三条非显然的决定:

1. **每块前缀所属小节标题**(`【送样要求】…`)。检索是按 chunk 打分的,脱离小节
   标题的段落经常丢掉「这段在讲什么」的关键词 —— 「厚度 4~5 μm」这一句不带
   「送样要求」就很难被「组织块要切多厚」召回。代价是每块多十几个字。
2. **H1 整行丢掉**。frontmatter 里已有 `title`,正文 H1 一般原样重复,留着会在首节
   生成一个十几字的纯标题 chunk —— 命中不了任何查询,却占一个候选位、拉低平均块长。
3. **超长段按句末标点切**(`。！？；!?;`),切不动才按 `CHUNK_MAX` 硬切。

`npm run kb:ingest -- --dry-run` 实测(2026-09-06):


## 3. 解析阶段独立先跑:宁可一篇不入,不入一半

`parseKnowledgeDirectory()` 在开事务之前独立跑完全部解析,**有一篇坏文档就整体不摄取**。
理由是知识库是引用来源:入一半会让 NovaGuard 反查到残缺的引用号,而那会直接触发
P0 质量事件 —— 一个格式笔误升级成一次发版冻结,代价完全不对等。

`_` 开头的文件被跳过(`_README.md` 是写给人看的约定说明,不是知识)。
文件按名排序摄取,保证摄取顺序确定、`ingest_runs.docs` 可逐次比对。

## 4. 事务回滚:为什么不是「失败后挨个 removeDocument」

这是 B3 唯一一处架构性选择,值得写清楚。

`indexDocument()` 是「按 doc id 删旧重插」的**幂等 upsert**。所以重跑一篇**已存在**
的文档,会先把旧 chunk 删掉。此时若靠 `removeDocument` 逐篇回滚:

> 新的删掉了、旧的也回不来 —— 修一版文案没通过回归,反而把库里原来能用的那版弄丢了。

SQLite 事务是唯一能真正还原到摄取前状态的办法。两处边界:

- `ensureSeeded()` 放在 `BEGIN` **之前** —— 种子库不属于本次摄取内容,不该被回滚掉;
- `ingest_runs` 日志行写在事务**之外** —— 回滚掉的摄取**更**需要留痕。

`--no-gate` 会在日志里如实记为 `gate-skipped`,不伪装成 `proceed`。

### 4.1 这条声明原本零测试覆盖,现已补上

`scripts/ingest-documents.ts` 整个建立在「门禁没过的知识一个 chunk 都不留」之上,
而在本次之前**没有任何测试验证过 ROLLBACK 分支**。新增 2 条(`ingest.test.ts`):

| 测试 | 验的是 |
|---|---|
| 门禁未通过时 ROLLBACK,库回到摄取前状态(含 FTS) | 改写文档 → `BEGIN` → 重摄取 → 断言**新文本此刻已可见**(这正是危险窗口,旧 chunk 已被 upsert 删掉)→ `ROLLBACK` → 断言 chunk 文本集合 `toEqual` 摄取前快照、`search(db,"切片厚度")` 仍有命中、`chunks_fts` 里匹配新文本 0 行 |
| 摄取途中抛错时 ROLLBACK,不留半篇入库的文档 | 事务内抛错 → 回滚 → 文档数回到基线 |

第一条特意断言 **FTS 影子表也一起回滚**。`chunks_fts` 是外部内容表,如果它的同步走
了事务之外的路径,回滚后就会留下指向已删 chunk 的索引行 —— 检索能查出来、取正文
时是空,那种状态比入库失败难查得多。

## 5. 门禁挂载与真实入库记录

流程:**解析 → 事务内入库 → 跑 NovaBench 金标回归 → `proceed` 才 COMMIT**。
不是「先灌再看」。

本地实际入库记录(`ingest_runs`,`.data/novapilot.db`):

```

  gate: {"decision":"proceed","failed":[],"maxTrafficPercent":10,
         "bench":"9/9 通过 (准确率 100%),引用有效性 100.0%,升级召回 100.0%"}
```

入库后库状态(现场核对):

| 项 | 值 |
|---|---|
| documents / chunks | **15 篇 / 54 chunk**(种子 7/22 + 摄取 8/32) |
| 带 512 维语义向量的 chunk | **54 / 54** |
| `chunks_fts` 行数 | **54**(与 chunks 一致) |
| 门禁回滚批次 | 0 |
| 整script 耗时 | 5.6 s(解析 + 语义模型加载 331 ms + 32 chunk 编码 + 入库 + NovaBench 9 例) |

**幂等性**:同目录二次摄取后库仍是 15 篇 / 54 chunk,不重复膨胀
(`indexDocument()` 的删旧重插语义)。

语义模型不可用时,摄取仍然成功、只写哈希向量,并打印
`装好模型后跑 npm run model:backfill 补齐` —— 摄取不该被向量后端的可用性阻塞

## 6. 四处埋点(指标体系 v1.1 第 12 节)

第 12 节点出现有系统缺四处采集。补上它们的目的**不是「多几张表」**,而是让看板上的
护栏对(第 10 节)真正成对有数 —— 只有激励指标有数、护栏指标没数的看板,比没有看板
更危险,因为它会让人以为自己在被约束。

第 12 节给的落地顺序 **A → D → B/C → 看板按第 10 节重组**,已按此顺序完成。

| 埋点 | 表 | 挂载点 | 服务的护栏对 |
|---|---|---|---|
| **A** 引用号反查审计 | `citation_audits` | `graph.ts:469` `recordCitationAudit()` | 可信解决率 ↔ 漏放率(生命线,目标 100%) |
| **B** 拦截/未转复核抽样 | `review_samples` | `graph.ts:491` `enqueueReviewSample()` | Critic 拦截率 ↔ 误拦截率;直接解决率 ↔ 该转未转率 |
| **C** 案例闭环入流 | `case_closures` | `api/expert-cases/route.ts:117` `recordCaseClosure()` | 知识入库量 ↔ 金标回归通过率 |
| **D** 隐式采纳事件 | `adoption_events` | `api/adoption/route.ts:35` `recordAdoptionEvent()` | 用户负反馈率 ↔ 隐式采纳率 |
| (补) 端到端延迟 | `latency_samples` | `api/consultations/route.ts:66` / `:115` | P95 延迟 ↔ 防线通过率结构 |

### 6.1 埋点 A:必须独立于生成路径

每出一张卡,就把卡上每个引用号拿回**本轮检索结果**里反查:在不在、是否 `verified`、
是否过期。判定(`auditCitations`,纯函数无 IO)与持久化(`recordCitationAudit`)分开,
所以判定可离线复现。

关键约束:**Critic 放行不等于绑定成立**,自己证明自己通过没有意义 —— 这是埋点 A
存在的全部理由。因此看板的「可信解决率」分子取自 `citation_audits`,而
**没有审计记录的 formal 卡不计入分子**:「没审过」不能当「审过且合格」。
绑定率 < 100% 时同时落一条 `quality_events`(P0)。

现场:`citation_audits` 11 行,加权绑定率 100%,`violatingCards = 0`。

### 6.2 埋点 B:两类样本抽样率刻意不同

```ts
export const DEFAULT_SAMPLE_RATES = { intercepted: 0.2, "not-escalated": 1 };
```

被拦错了用户当场就会抱怨(有自然反馈通路);**该转未转错了没有任何人会来报错**,
只能靠抽样把它捞出来。给这两类同一个抽样率,等于把复核人力平均分给「已经有别的
办法能发现的问题」和「除了抽样别无办法的问题」。

抽样用 traceId 的 FNV-1a 哈希(`stableUnit`),**不用 `Math.random`** —— 同一个
traceId 永远得到同一个值,抽样结果可复现,离线回灌能得到同一批样本。

复核结果分两级:`setJudgeVerdict`(LLM 初判,`npm run review:judge`)与
`setExpertVerdict`(人工终判),`reviewSampleSummary` 用二者比对算出
**judge–专家一致率**。一致率 < 85% 时(第 11 节 P1)判定的是「judge 的结论还不能
替代专家」,而不是「系统有问题」—— 这一格是给自动化复核本身设的门槛。

### 6.3 埋点 C:唯一一处**故意抛错**的埋点

`recordCaseClosure()` 在 `producedCandidate === false` 且没给理由时**抛
`MissingNoCandidateReason`**,而 A/B/D 都吞异常(埋点写失败不该让用户拿不到卡)。

差别的理由:A/B/D 丢一条样本只是分母漂一点;而埋点 C 一旦允许「结案了、没产候选、
也不说为什么」,「知识入库量」这个激励指标的分母就可以被静默做小 —— 结的案不
算进分母,入流率永远好看。让它抛错,是让这条路径**在代码层面走不通**。

现场:`case_closures` 0 行(暂无专家结案),入流率显示 `—` 而非 `0%`。

### 6.4 埋点 D:`sync` 没有 UI 触发点,这是有意的

`ADOPTION_ACTIONS = ["copy", "export", "sync"]` 三个动作里,`copy` 和 `export` 都有
前端触发,**`sync` 目前没有**。原因必须写下来,否则后人会把它当成漏做的接线:

> 飞书多维表双写(`graph.ts:421`)是**每张卡自动执行**的,不是用户动作。
> 如果把它计入采纳事件,采纳率会被推到 ~100%,这个指标就彻底失去分辨力 ——
> 正是第 4.4 节点名的游戏化失败模式。

所以 `sync` 保留在枚举里(留给将来真正由用户触发的「同步到我的项目」动作),
但**不接自动双写**。第 4.4 节的另一条边界也一并守住:**采纳率不进「可信解决率」
的计算链**,它只作为负反馈率的成对护栏出现。

现场:`adoption_events` 1 行(一次 copy)。

### 6.5 补的那一格:端到端延迟

第 10 节要求 P95 延迟必须与**防线通过率结构**成对看(「优化延迟不得以防线为代价」),
而改造前系统里一个延迟数都没落库。两条本来可以走的捷径都被否掉:

- **标成「未接入」** —— 那一行护栏对就是排版上的成对;
- **拿 `retrieval.ts` 的 `elapsedMs` 充当端到端 P95** —— 它只覆盖检索一段,
  标成端到端是**偷换口径**,而这张看板存在的意义就是防这件事。

所以新建 `latency_samples`(`SCHEMA_VERSION` 6 → 7),在 `consultations` 与
`consultations:stream` 两条路径各采一次墙上时钟毫秒。两个设计点:

1. **样本带 `card_status`**。一个状态盲的全局 P95 分不出「真的变快了」和
   「把该升级的问题硬答了」—— 而后者正是第 10 节给这一行点名的游戏化路径。
   formal 与 expert-review 的延迟必须分开看。
2. **流式路径只量到 `respond` 返回**,不含 SSE 帧推送时间 —— 那部分取决于客户端
   读取速度,算进服务端延迟会让同一次咨询在不同网络下出不同的 P95。

P95 用**最近秩(nearest-rank),不插值**:

> 样本量小的时候插值会造出一个没人经历过的延迟值 —— 3 条样本插出来的 P95 是
> 算术产物,不是任何一次真实请求的耗时。宁可返回真实存在的那一条。

现场实测(3 次真实咨询:formal / expert-review / chat):
P50 23 ms · P95 50 ms · 分状态 `formal 50 ms · expert-review 23 ms · chat 4 ms`。

## 7. 看板按第 10 节护栏对重组

`guardrailBoard(db, sinceIso)` 一次算完六对,**同源同窗**。这一点是结构性的:

> 如果护栏侧和激励侧来自两次独立查询、两个不同时间窗,那么「成对」只是排版上的
> 成对 —— 有人优化了激励指标,护栏侧还显示着上周的数,看板会给他一个通过。

`PairRow` 类型强制 `guardrail` 与 `guardrailValue` 必填,所以**这张板在类型层面
放不下一个孤零零的激励指标**:想加一个激励指标,就必须同时写出它的护栏。

默认切窗 `weekStart()`(周一 00:00 UTC)—— 第 11 节的复盘节奏是周会,看板窗口和
复盘窗口对不上的话,会上讨论的数和板上显示的数不是同一批。

### 7.1 分母是会话数,不是卡版本数

`decision_cards` 主键是 `(id, version)`:同一个咨询改一次事实就重出一版、多一行。
拿行数当分母,一个反复修参数的用户会把分母冲大、解决率冲低,而他其实只咨询了
一件事。所以按 `trace_id` 去重(一次图运行 = 一次会话 = 一个 trace),
`trace_id` 为空的历史行退回 `id||':'||version` 而不是静默丢弃 —— 丢样本会让分母漂。

### 7.2 null 不是 0,一路守到渲染

`ReviewRate.rate`、`LatencyStats.p50/p95`、`FeedbackMix.negativeRate` 和三个会话率
全部是 `number | null`,`pctOrDash` / `msOrDash` 把 null 渲染成 `—`:

> 一个写着 0% 误拦率的空队列会让人以为系统已经被验证过了。这一个字符的差别是
> 「这项还没人验证」和「验证过,没问题」之间的全部差别。

`p1Breaches()` 同理**跳过** null:把 null 当 0 会静默地把一个没被验证过的系统标成健康。

### 7.3 一个我自己踩的静默归零 bug(以及三条对策)

看板上线后显示 `全库 0 篇 / 0 段`,而库里实实在在有 15 篇 / 54 chunk。

根因:`knowledgeVolume` 查了 `documents.created_at` —— **这一列不存在**
(`documents` 表没有时间戳)。而我为「老库缺表时不让整页 500」加的 `safe()` try/catch
把 SQLite 错误吞成了全零兜底。**这恰好就是这张看板存在的目的所要防的失败模式**:
一个写错的列名被吞成「这一格是 0」,而 0 在看板上和真实的 0 长得一模一样。

三条对策:

1. **换数据源**:入库量的数据源改为 `ingest_runs`(有时间戳,而且带门禁判定)。
   顺带两个收益 —— 入库量正确地成为**流量**指标;`rolledBackRuns` 成为「灌水入库」
   这条游戏化路径的**直接观测量**。另加不切窗的 `documentsTotal`/`chunksTotal`,
   因为「本周 +0 篇」会被读成「知识库是空的」,而这两件事的处置完全不同。
2. **`safe()` 改用 `console.error` 并带 `口径缺格` 字样**,起服务时看得见。
3. **新增 describe 块「每格都必须真的读到数」(4 条)**,每条都断言一个 `> 0` 的值 ——
   只断言 0 的测试对这类错误**完全免疫**。

修复后现场:`本周 +8 篇` / `全库 15 篇 / 54 段 · 本周门禁回滚 0 批`。
